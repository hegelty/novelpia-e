## 노벨피아e 0.1.1 내서재 호환 수정 (2026-10-06)

`versionName`을 `0.1.1`로, `versionCode`를 `2`에서 `3`으로 올렸습니다.
내서재 API 주소는 그대로이며, 작품 행을 감싸는 `mybook-selection-row` 요소를
허용하도록 파서를 수정했습니다. 기존 직계 작품 행도 지원합니다.

| 검사 | 결과 |
|---|---|
| 로그인된 실제 HTML 비교 | 같은 선호작·최근 기록 응답에서 기존 파서는 실패하고 수정한 파서는 통과했습니다. |
| 선호작·최근 기록의 1·2페이지 | 각 30개 작품과 이어보기 정보, 이전·다음 페이지를 정상적으로 읽었습니다. |
| 알림·소장 목록 | 실제 계정의 빈 목록을 정상적으로 읽었습니다. 작품이 있는 경우는 합성 예제로 검증했습니다. |
| Java 단위 테스트 | 205개가 통과했습니다. |
| 빌드 | API 19 jar를 지정한 수동 빌드와 APK 서명 검증을 통과했습니다. |
| 업데이트 메타데이터 | 완성된 APK에서 동일한 application ID와 버전 `0.1.1` / `3`을 확인했습니다. |
| 서명 호환성 | GitHub에서 받은 기존 v0.1.0 공개 APK와 서명 인증서의 SHA-256이 일치했습니다. |

### 이전 — 이름·저장 로그인·내서재 정보/정렬 (2026-09-27)

- 앱 표시 이름을 **노벨피아 e-ink**로 변경했다. 홈의 홍보성 문구·장식 문구를 제거했다.
- 선택적 비밀번호 저장·자동 로그인을 구현했다. 자동 로그인은 이메일 로그인만
  대상으로 하며, 앱 시작 시 한 번 시도한다. Google OAuth를 구현한 것은 아니다.
- 선호작·알림·소장·최근 기록 탭, 마지막 읽은 회차/전체 회차 수/작가,
  공개일자순·조회순·등록순·추천순, 그룹 필터, 서재 검색/해제를 연결했다.
  최근 기록은 실제 사이트처럼 정렬·그룹 선택을 제공하지 않는다.
- 목록의 전체 회차 수는 사이트의 `회차` 필드다. **뷰어 ID나 전체 회차 수를
  최신 회차 고유 ID로 오인하지 않으며**, 미제공 값은 추정하지 않는다.

실제 HTML 검사 범위: 선호작 기본 및 정렬 3종, 조회순 2쪽, 미분류, 최근 기록,
빈 알림·소장, 검색 결과 없음, 한글 검색 결과 있음. 각 응답의 회차 정보 포함
개수와 정렬·그룹 옵션 수, 이전/다음 존재 여부만 출력했다. HTML은 브라우저→JVM
메모리에서만 전달했으며 파일에 저장하지 않았다. 쿠키·비밀번호를 내보내거나
실계정 작품명·본문을 로그에 기록하지 않았다. **브라우저 인증 응답의 파서 검증과
새 네이티브 UI의 실제 계정 로그인 검증은 서로 다르다.**

보안 검토에서 AES 키와 HMAC 키 모두 RSA로 감싸도록 수정했고, 비밀번호 공백
제거와 추가 바이트를 허용하던 처리를 제거했다. 암호문 개별 바이트가 우연히
평문 바이트와 같을 수 없다고 가정하던 테스트도 올바른 전체 페이로드 검사로
수정했다. 저장 검사는 프로덕션과 분리된 `synthetic_test` 키/환경설정만 사용한다.
실제 저장 자격 증명이 있으면 instrumentation은 Activity 실행 전에 검사를 거부한다.

실제 계정의 **저장 후 프로세스 재시작 → 자동 로그인 → 서재 표시**는 사용자가
새 앱에서 직접 비밀번호를 입력하고 저장 옵션을 켠 뒤 추가 확인해야 한다.
검증을 위해 실제 비밀번호를 읽거나 다른 브라우저에서 추출하지 않았다.
크레마 실기기·Google 세션 전송·유료 회차·그룹 생성/삭제/작품 이동은 미검증 또는
미구현 범위다. 이번 변경에 그룹 편집이나 선호작/기록 삭제 기능은 포함하지 않는다.

당시 APK: `dist/novelia-0.1.0-preview.apk`, **4,449,591 bytes (4.24 MiB)**.
SHA-256: `09551e106346e0930b9c583722af90e3f2d9f594cf361f00b1d7d9f443d71fce`.
빌드 로그: `/tmp/novelia-shelf-auth-build-3.log` 및 최종 테스트 픽스처 정리 후
`/tmp/novelia-shelf-auth-build-4.log`.

최종 APK를 다시 설치한 뒤 17개 검사를 재실행해 모두 통과했다.
합성 화면 PNG 12개를 `dist/screenshots/`에 갱신했고, 이번에 바뀐 홈·최근 기록·
선호작·빈 목록·정렬 선택창·빈 로그인 화면을 직접 열어 확인했다.
정렬 4개가 한 화면에 표시되고 첫 목록의 이전 버튼이 비활성인 것을 확인했다.
`ui-login.png`에는 이메일·비밀번호가 입력되지 않았다. 실제 계정 화면 캡처나
비밀번호 저장 파일은 결과물에 포함하지 않는다. 검사 후 앱을 시작 화면에 열어 두었다.

이전 서재 UI의 결과이며 이번 UI 개편의 재로그인 성공으로 간주하지 않는다.
업데이트와 instrumentation으로 기존 메모리 세션은 종료되었다.

### 계정 연동

초기 계정 빌드에는 이메일 로그인, 회원 상태 검증, PC 로그인 세션 가져오기와
최애 작품(최대 5개) 조회를 추가했습니다. 당시 최근 본 작품/전체 선호작은 미구현이었습니다.
사용자 제공 계정 연동 검사 화면에서 이메일 로그인 후
**“로그인 상태: 서버에서 확인됨”**을 확인했습니다. 이는 사용자 실행 결과이며,
개발 도구로 자격증명이나 세션을 수집해 재현한 결과는 아닙니다.
동일 화면에서 최애 작품은 조회 미확인으로 표시되어 목록 연동 성공은 아닙니다.
이후 진단/AJAX 수정 빌드에서 사용자가 다시 이메일 로그인했고, 개발자가
`tools/account_ui_check.py`로 실제 메뉴를 조작해
`{"login":"authenticated","favorites_count":0}`을 확인했습니다.
사용자도 최애 작품이 실제로 0개라고 확인했습니다. 따라서 **이메일 로그인과
빈 최애 목록 조회는 실계정 검증 완료**입니다. 비어 있지 않은 최애 목록은
합성 테스트만 수행했으며 실계정으로 확인한 것은 아닙니다.
구글 계정은 사용자가 PC 공식 사이트에서 직접 로그인하고 로컬 세션 파일을
앱에서 선택합니다(`docs/GOOGLE_LOGIN.md`). 비밀번호·쿠키·계정 식별자를
채팅이나 테스트 로그에 전달하지 않습니다. 구글 계정의 PC 세션 가져오기는
사용자 재시도 후에도 로그인 필요로 표시됐으며, 원인은 미확정입니다.
이후 최근 본 작품·전체 선호작을 구현했습니다. 다음 절의 후속 검증과 구분합니다.

### 최근 기록·전체 선호작 후속 검증

- 사용자 직접 로그인한 별도 로컬 Chromium에서 인증 확인.
- 두 목록의 실제 서버 렌더링 HTML, 작품 행, 마지막 회차 링크, 페이지 링크 확인.

  선호작 30/30/10개, 최근 기록 30/30/2개.

- API 19의 별도 `app_process`에서 합성 쿠키 검사 통과:
  여러 쿠키, 점 접두사 없는 apex 쿠키, 서브도메인/경로 제한,
  서버 `Set-Cookie` 교체, 잘못된 가져오기의 원자적 거절.
  실제 `HttpsURLConnection.getRequestProperties()`에서도 모든 해당 쿠키가
  하나의 `Cookie` 헤더에 들어가는 것을 확인. 네트워크 전송은 하지 않음.
- 이 검사를 위해 사용자 앱을 재설치/재시작하거나 실제 세션을 사용하지 않음.
- 확장 v1.1.0에 활성 탭 로그인 표시 검사, 해당 탭의 cookie store 선택,
  안전한 쿠키 개수 안내 추가. Node 모의 테스트 통과.
  사용자는 새 버전으로 1개 쿠키를 재내보냈으나 앱에서는 같은 로그인 필요 결과.

## 직접 조작 및 추가 진단

- 사용자의 직접 조작 요청에 따라 에뮬레이터의 최애 작품 메뉴를 실제로 열고,
  알려진 오류 문구만 추출해 “선호작을 불러오지 못했습니다.”를 확인했습니다.
  이전 코드의 비-200 JSON `status` 분기에 해당합니다. 실제 숫자 코드는 미확인.
- 기존 세션을 유지하려고 제한적인 라이브 진단을 시도했으나 완료 전에
  에뮬레이터가 ADB에서 사라졌고 호스트 프로세스도 종료됐습니다.
  호스트 로그에는 원인이 남지 않아 정확한 종료 원인은 미확정입니다.
  상태 코드·응답 원문·쿠키는 이 시도로 얻지 못했습니다.
  기존 메모리 세션은 잃었으며, 같은 라이브 디버그 방식은 재시도하지 않습니다.
- 기존 userdata/SD 이미지를 유지해 ARM 에뮬레이터를 다시 부팅했습니다.
  이후 진단은 앱이 직접 생성한 안전한 오류 코드와 UI 조작만 사용합니다.
- 비로그인 공개 요청 비교에서는 AJAX 헤더 유무 모두 HTTP 200 / JSON status 401.
  인증 후의 실패 원인이나 AJAX 헤더 수정 효과를 증명하는 결과는 아닙니다.
- `tools/account_ui_check.py --self-test` 통과. 이 도구는 설치/재시작/로그인이나
  디버거 연결을 하지 않으며, 알려진 검사 버튼만 조작하고 요약 결과만 출력합니다.
  복구한 에뮬레이터에서도 실제 UI 조작으로 `{"login":"unauthenticated"}` 출력 확인.
  이후 사용자 재로그인 후 `{"login":"authenticated","favorites_count":0}`도
  직접 확인했으며 사용자가 실제 최애 작품 0개와 일치한다고 확인했습니다.
